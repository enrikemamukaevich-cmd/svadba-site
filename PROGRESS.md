### Открытая проблема 9: боевой адрес недоступен с машины Энрике

Сервер жив и отдаёт сайт — это проверено с независимой сети, страница
возвращается целиком. С компьютера Энрике до него не доходит.

Виноват VPN. В системе поднят туннель `happ-tun` (`sing-tun`, клиент Happ),
он держит весь трафик: шлюз `172.18.0.2`, метрика 0. Плюс включён прокси
Windows `127.0.0.1:10809` и те же `HTTP_PROXY`/`HTTPS_PROXY` в переменных среды.

Признаки, по которым это видно:

- `tracert` до `201.34.133.135` кончается на первом же прыжке за <1 мс —
  до Москвы так не бывает, отвечает сам туннель;
- порты 22, 80 и 443 «открыты» за 2 мс, но SSH обрывается на `banner exchange`,
  а HTTP молчит до конца срока ожидания: рукопожатие завершает туннель, дальше
  него ничего не идёт;
- через тот же туннель `timeweb.cloud` отдаёт 200, то есть дело не в сети вообще,
  а именно в маршруте до этого адреса.

Выключить туннель нельзя: через него работает сам Claude Code.

**Что пробовали и почему не вышло.** Конфиг Happ лежит в
`%LOCALAPPDATA%\Happ\config.json`, это обычный `sing-box` с секцией
`route.rules` и готовым выходом `direct` — правило для нашего адреса туда
вписать можно. Не помогает по двум причинам. Первая: журнал `happd.log`
показывает подъём туннеля в 17:23:59, ровно время записи `config.json`, —
Happ пересобирает конфиг при каждом подключении, и правка не переживёт
переподключение. Вторая: внешнего пульта (Clash API) в конфиге нет, значит
применить правку можно только перезапуском туннеля, а это обрыв доступа.

Отдельно проверялся обход через первое правило конфига, которое пускает мимо
туннеля процессы с именами `xray.exe` и `sing-box.exe`: копия `curl.exe` под
таким именем действительно уходит другим маршрутом, но упирается в
`strict_route: true` — не открывается вообще ничего, даже `ya.ru`. Тупик.

**Поэтому заливка переехала на GitHub-посредник**, смотри раздел ниже.
Сетевые настройки Claude не менял: прав администратора у сеанса нет,
`route add` и `Disable-NetAdapter` отбились с `requires elevation`
и `Access is denied`.

## Внимание: окно приёма в базе сдвинуто

На 04.08.2026 в таблице `settings` стоит `window_start` = `2026-08-03 12:00:00+03`,
хотя жёсткая константа в памятке — 06.08.2026 12:00. Кто-то передвинул его
уже в ходе работы: в начале сессии там было 6 августа. Claude настройку
не менял.

Из этого следуют две вещи. Первая: **приём фото сейчас открыт**, сайт пускает
гостей загружать снимки уже сегодня. Если это делалось для проверки с айфона —
не забыть вернуть 6 августа перед свадьбой. Вторая: текст «Откроется 6 августа
в 12:00» в `app.js` вписан числом и за настройкой не следует, поэтому пока
`window_start` стоит на 3 августа, сообщение расходится с делом. Трогать его
не стал: числа в памятке никто не отменял, а расхождение временное.

Проверки этапов 3 и 4 теперь берут границы окна из базы и считают моменты
от них, а не вписывают даты числами, — иначе любой сдвиг настройки роняет
проверку там, где лента работает правильно.

### Что нужно от Энрике: программа удаления снимка

Удалять записи публичным ключом нельзя — `anon` выдан только `SELECT` и `INSERT`.
Это правильно: иначе любой гость стёр бы чужие фото. Проверять, что снимок свой,
надо по скрытому ключу `secret`, а он наружу не отдаётся. Значит нужна программа
внутри базы. Выполнить в SQL-редакторе Supabase один раз:

```sql
create or replace function delete_photo(p_secret uuid, p_photo_id uuid)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_guest uuid;
begin
  select id into v_guest from guests where secret = p_secret;
  if v_guest is null then return jsonb_build_object('ok', false, 'error', 'no_guest'); end if;
  delete from photos where id = p_photo_id and guest_id = v_guest;
  if not found then return jsonb_build_object('ok', false, 'error', 'not_yours'); end if;
  return jsonb_build_object('ok', true);
end $$;

grant execute on function delete_photo(uuid, uuid) to anon;
```

Лента уже умеет её звать и ничего в коде менять не надо. Файл снимка в хранилище
эта программа не трогает — его уберёт панель владельца на этапе 6.

### Как запускать проверки

Playwright теперь стоит прямо в папке проекта — `package.json` и `node_modules`
на 18 МБ. Возиться с `NODE_PATH`, как раньше, больше не нужно, проверки
запускаются короткими командами:

```
npm run test:4      только этап 4
npm test            все три этапа подряд
npm run photos      пересобрать исходники для этапа 4
npm run measure     замерить вес превью, ничего не отправляя
npm run serve       поднять сайт локально на 8123
```

Сам сайт по-прежнему без единой зависимости: `package.json` нужен только
проверкам, помечен `private`, и `deploy.ps1` его не заливает.

## Секреты

Утечек нет. В `app.js` лежит `SUPABASE_KEY: 'sb_publishable_…'` —
публикуемый ключ, он по замыслу открыт и защищён политиками RLS
на стороне Supabase. Ключей `service_role`, приватных ключей и паролей
